### 2.1 “高优先级库”的命名和实现

“高优先级库”在本计划中首先是逻辑优先级，不默认新建 dataset。建立一张非敏感的 `dataset-priority-registry`（可放在团队运营文档或 Dify workspace 说明中），每行至少包含：Dify dataset 显示名、逻辑层级、主题、资料状态、负责人、启用日期、停用日期、备注。

采用以下命名约定：

| 逻辑层级 | 含义 | 当前映射 | Workflow 顺序 |
|---|---|---|---|
| `P1` 高优先级 | 已审核、与当前业务直接相关、允许优先作为事实依据的资料范围 | `产品与解决方案` 中已由业务负责人确认的 5 份正式资料；使用 `priority=P1` 元数据过滤 | 第一段检索 |
| `P2` 主题库 | 已按主题归档但尚未列入 P1 的正式资料 | `行业与市场研究`；当前 `产品与解决方案` 无剩余 P2 文件 | P1 无命中后检索 |
| `P3` 待分类库 | 尚未完成主题确认或审核的资料 | `待分类` landing dataset；已创建，当前 0 份资料 | P2 无命中后检索 |

先在 Dify 1.16.1 中启用并验证 Knowledge Retrieval 的文档级元数据过滤；沿用现有 dataset，并以 `priority=P1/P2/P3`、`topic=...`、`status=approved/pending` 作为检索过滤条件。当前 5 份 `产品与解决方案` 文件登记为 P1，`行业与市场研究` 登记为 P2；`待分类` 仅在 P2-02 需要 P3 节点时创建为空 landing dataset。若 live UI 权限或 license 导致元数据过滤不可用，才按文档边界将已审批 P1 文件迁移到独立 dataset，等待索引和召回验证通过后再从原 dataset 移除；不得仅因为名称歧义重复创建现有主题库。后续新增文件必须先确定主题和优先级，再进入对应 dataset；无法判断主题时才进入 P3。

### 2.2 路由总览

```text
Start
  -> Code: 规范化问题/识别联网意图
  -> IF: time_sensitive OR explicit_web_request
       true  -> Tavily Search -> Code: 规范化联网结果 -> LLM/Answer
       false -> Knowledge Retrieval: P1
                  -> Code: 规范化 P1 结果
                  -> IF: p1_hit
                       true  -> LLM/Answer（禁止继续低优先级检索）
                       false -> Knowledge Retrieval: P2 主题库
                                  -> Code: 规范化 P2 结果
                                  -> IF: p2_hit
                                       true  -> LLM/Answer（禁止查 P3）
                                       false -> Knowledge Retrieval: P3 待分类库
                                                  -> Code: 规范化 P3 结果
                                                  -> IF: p3_hit
                                                       true -> LLM/Answer
                                                       false -> Tavily Search -> LLM/Answer
```

时间敏感或明确要求联网的问题走联网分支，不先查库。非联网问题严格执行 P1 -> P2 -> P3：P1 命中即停止低优先级检索；P2 命中即不查 P3；只有全部未命中才调用 Tavily。联网分支的结果不得被伪装为知识库事实，回答中必须保留来源/链接字段（由 Tavily 输出提供）。

## 4. Workflow 节点与变量设计

Workflow 名称建议为 `phase2-knowledge-routing`，先保存为 draft，完成测试后再 Publish。

### 4.1 Start 输入变量

| 变量 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `question` | String | 是 | 用户原始问题 |
| `need_web` | Boolean | 否 | 用户明确要求联网时可由调用方传入；缺省为 `false` |
| `conversation_id` | String | 否 | 仅用于会话关联，不作为知识检索条件 |

### 4.2 节点配置

| 节点 | Dify 节点类型 | 关键配置/输出 |
|---|---|---|
| `Start` | Start | 暴露上述变量 |
| `Normalize Question` | Code | 输入 `question`, `need_web`；输出 `normalized_query`、`explicit_web`、`time_sensitive`、`route_reason`。检测“联网/网上/最新/截至/今天/本周/当前/实时”等明确实时意图；`need_web=true` 直接为 true。字符串为空或仅空白时输出 `invalid_query=true`，进入统一失败回答，不调用 Tavily。 |
| `Web Intent IF` | IF/ELSE | 条件 `explicit_web == true OR time_sensitive == true`。true 直接进入 Tavily；false 进入 P1。 |
| `Retrieve P1` | Knowledge Retrieval | 只选择登记表启用的 P1 dataset；若未实现文档级过滤，则只能选择已隔离的 `P1-<主题>` dataset，查询 `normalized_query`，Top K=3；不勾选 P2/P3 dataset。输出原始检索结果。 |
| `Normalize P1` | Code | 输入检索输出 `result`；输出 `p1_hit`、`p1_evidence`、`p1_count`、`p1_quality_note`。 |
| `P1 Hit IF` | IF/ELSE | `p1_hit == true` 为 true 时直接到 `Answer from KB`，不得连接 P2/P3。 |
| `Retrieve P2 Topics` | Knowledge Retrieval | 选择登记表启用的 P2 主题 dataset（或完成 P1 隔离后现有主题库中保留的 P2 文档）；不选择 P1/P3。 |
| `Normalize P2` | Code | 输出 `p2_hit`、`p2_evidence`、`p2_count`、`p2_quality_note`。 |
| `P2 Hit IF` | IF/ELSE | `p2_hit == true` 时直接到 `Answer from KB`，不得连接 P3。 |
| `Retrieve P3 Unclassified` | Knowledge Retrieval | 只选择 `待分类` dataset；为空时节点应返回空数组并继续，而不是报错。 |
| `Normalize P3` | Code | 输出 `p3_hit`、`p3_evidence`、`p3_count`、`p3_quality_note`。 |
| `P3 Hit IF` | IF/ELSE | 命中则到 `Answer from KB`；未命中则到 Tavily。 |
| `Tavily Search` | Tool | 使用已配置的 Tavily plugin；query=`normalized_query`；结果数量沿用冒烟测试的收敛配置，必须保留标题、URL、摘要/片段。 |
| `Normalize Web` | Code | 将 Tavily 结果统一为 `web_evidence[]`，空结果输出 `web_hit=false` 和明确原因。 |
| `Answer from KB` | LLM | 输入命中的最高优先级证据及 `route_reason`；只引用本次命中的层级，不能声称查过被跳过的低优先级库。无证据不得补写事实。 |
| `Answer from Web` | LLM | 输入 `web_evidence[]`；要求给出来源链接和检索时点说明，区分事实、推断和未知。 |
| `Invalid/Failure Answer` | Answer/LLM | 对空问题、检索服务失败或 Tavily 空结果返回可操作提示，并输出内部可记录的 `failure_reason`，不泄露系统配置。 |

### 4.3 Code 节点规范化规则

Dify 的 Knowledge Retrieval 输出可能是数组、包含 `result` 的对象或序列化 JSON 字符串；每个 Code 节点都必须先尝试解析这三种形态，再读取 chunk 的 `content/text`、`score`、`metadata`。不把“节点成功执行”当作命中。

统一规则：去除空 chunk；`count` 为有效文本 chunk 数；`hit=true` 仅当存在有效文本且（有分数时最高分达到当前 Dify 配置的有效召回基线，或无分数字段但文本与 query 有明确关键词重合）成立。将最多 3 条证据投影为 `{content, score, source, dataset}`，source 缺失时写 `unknown`，不在回答中伪造来源。若解析失败，输出 `hit=false`、`count=0`，并记录 `empty_result` 或规范化错误，按失败路径处理。

为便于在 Dify Code 节点直接实现，所有规范化节点使用相同的输入名 `retrieval_result` 和输出字段；P1/P2/P3 仅改变前缀。代码只做类型转换、空值处理、计数和证据截断，不调用网络、不读取文件、不存储资料。

## 5. 按日期实施步骤

### 08-10：登记优先级，搭建 P1 路由

- 在 Dify Knowledge 中盘点现有 dataset、索引状态、文档数和主题归属；建立 `dataset-priority-registry`。不新建与现有主题库重复的 dataset。
- 先用一个受控检索配置验证 Dify 是否能按文档元数据隔离 P1；若不能，按文档状态盘点混合 dataset，将确需优先的已审批文档导入 `P1-<主题>`，等待索引和召回验证通过后再从原 dataset 移除；如果整个现有 dataset 都满足同一层级，则直接登记现有 dataset，不创建新库。
- 按已记录的业务确认，将 `产品与解决方案` 中的 5 份正式资料登记为 P1；在 Dify 中为这 5 份文件写入 `priority=P1`（以及必要的 `topic`/`status`）元数据，不新建重复 P1 库。
- 在 Studio 创建 `phase2-knowledge-routing` draft，配置 `Start`、`Normalize Question`、`Web Intent IF`、`Retrieve P1`、`Normalize P1`、`P1 Hit IF`。
- 用一条明确命中 P1 的非敏感问题调试，确认得到 P1 证据后流程结束，不出现 P2/P3/Tavily 调用。
- 保存 draft 版本和问题编号；失败时先修正节点变量映射，不修改知识库内容。

### 08-11：接入 P2/P3 并完成严格短路

- 配置 `Retrieve P2 Topics`、`Normalize P2`、`P2 Hit IF`、`Retrieve P3 Unclassified`、`Normalize P3`、`P3 Hit IF`，将分支连接到统一回答和 Tavily 节点。
- 确认现有 P3 dataset 的空库行为；若不存在，在 Dify 中按 `待分类` 建立 landing dataset，并注明当前 0 份资料，不上传虚构内容。
- 完成三类验证：P1 命中停止低优先级；P1 未命中且 P2 命中不查 P3；P1/P2 未命中且 P3 为空才到 Tavily。
- 记录每次节点实际执行路径。只有所有路径符合短路规则，才将 draft 标记为“可进入条件分支测试”。

### 08-12：完成联网与知识库条件分支

- 完善 `explicit_web`、`time_sensitive` 判断和 `Web Intent IF`；时间敏感/明确联网问题直接 Tavily，不进行 P1/P2/P3 检索。
- 将 Tavily 结果接入 `Normalize Web` 和 `Answer from Web`；回答必须显示来源链接，空结果进入失败回答。
- 发布一个可回滚版本，在 Dify Debug/Preview 中执行本节测试矩阵；保存路由结果和问题编号，不保存资料原文。
- 检查非联网问题的“知识库全未命中才联网”规则，避免把一般问题误判成联网问题。

### 08-13：建立待分类运营机制并完成既有资料验证

- 明确角色：资料整理责任人为市场/业务指定运营人；Dify 导入与索引验证责任人为知识库运营人；主题判定和 P1 提升审批人为业务负责人；Workflow 发布和回滚责任人为工程师/系统管理员。姓名放在团队内部台账，不写入仓库计划。
- 固定节奏：每周完成资料收集、主题判定、去重、批量导入和抽样召回复核；紧急资料可单独导入，但不得跳过审核和台账。IMA 待整理清单在联通恢复后再纳入该节奏。
- 使用阶段一已导入的 5 份市场部正式资料完成本阶段验证，不新增测试文档，不等待 IMA 导出资料；新增文件直接按主题导入对应正式主题库，无法判定主题的才进入 `待分类`。
- 等待每个文档 `Completed`，用独特短语进行召回验证，记录 batch id、日期、操作人、目的 dataset、数量、索引结果和验证结论。

## 6. 测试问题与预期

测试问题可使用业务负责人确认的非敏感变体；下表给出问题类型和必须观察到的路径。

**验证资料基线：**所有需要命中文档的测试（尤其 R1、R2、R4、R5）只使用阶段一已导入并验证的 5 份市场部正式资料；P3 空库和联网分支使用不命中这 5 份资料的非敏感问题，不上传新测试文档。

| 编号 | 问题类型/示例 | 预期路径与结果 |
|---|---|---|
| R1 | 业务负责人从已确认的 P1 资料中现场选取一条唯一短语提问（短语不写入仓库） | 命中 P1，输出对应 chunk；P2、P3、Tavily 均不执行。 |
| R2 | “行业与市场研究中关于目标市场变化的判断是什么？” | P1 无命中，命中 `行业与市场研究` P2；不执行 P3 和 Tavily。 |
| R3 | P3 命中/空库：有真实待分类资料时使用业务负责人选取的唯一短语；当前为空时使用一个不命中 P1/P2 的非敏感问题 | 有资料时命中 P3，回答标注尚未完成主题审核；空库时 P3 返回空数组并继续 Tavily；不构造测试文档。 |
| R4 | “请联网查询 2026 年当前工业自动化市场趋势。” | `explicit_web/time_sensitive=true`，直接 Tavily；知识库节点不执行，回答含 URL 和时间说明。 |
| R5 | “公司正式资料中没有覆盖的某个冷门问题是什么？” | 非联网；P1、P2、P3 均无有效命中后才 Tavily。 |
| R6 | “截至今天，某指标最新值是多少？” | 直接 Tavily，即使知识库可能有旧资料；回答不能把旧资料当最新值。 |
| R7 | 空字符串或仅空格 | `invalid_query=true`，返回补充问题提示；不调用 Knowledge Retrieval 和 Tavily。 |
| R8 | Tavily plugin 暂时失败/返回空数组 | `web_hit=false`，返回无法完成联网检索的可操作提示；记录失败原因，不编造结果。 |
| R9 | P1 返回无文本 chunk 或解析异常 | 视为 P1 未命中并记录规范化失败（如 `empty_result`）；继续按失败策略处理，不因节点成功状态短路。 |
| R10 | 同一源文件重复导入 | 台账和文件标识检查发现重复；不重复上传，或删除错误副本后只保留一次并重新验证。 |

验收时除最终回答外，必须观察 Debug 面板的节点执行路径，确认“停止低优先级检索”是真实未执行，而不是回答文字声称未执行。

## 7. 失败处理、风险与回滚

### 7.1 失败处理

- **Knowledge Retrieval 节点报错：**保留错误节点和时间，检查 dataset 权限、索引状态、模型配置和变量映射；修复后只重跑该问题。连续失败时切换到已验证的 Workflow 版本，不删除原版本。
- **规范化失败：**将输入类型视为不可信，按 `hit=false` 处理并记录 `empty_result` 或规范化错误；修复 Code 节点后重测数组、对象和 JSON 字符串三种形态。
- **P1/P2/P3 误路由：**先禁用错误 dataset 的路由连接，恢复上一版本；检查 priority registry 和 dataset 选择，再以 R1-R3 重测。
- **Tavily 失败、超时或无结果：**不把失败当作知识库命中；输出“当前无法完成联网检索”，检查插件配置、额度、网络和结果字段，不在仓库或日志中打印 key。
- **导入/索引失败：**按文件重试，必要时在 `.md`、Word `.doc/.docx` 和 `.pdf` 之间选择可解析的版本；图片-only 内容留待 OCR 阶段，不导入空文本。
- **误答或引用不可信：**将问题、路径、dataset 层级和结论记录为匿名样本，降低该资料范围优先级或移出 dataset，重新索引并回归测试。

### 7.2 风险和回滚

| 风险 | 预防/监控 | 回滚动作 |
|---|---|---|
| P1 命中后仍查询低优先级库，增加延迟或混淆证据 | Debug 观察节点执行图；P1 IF 不连接低优先级节点 | 恢复上一 Workflow 发布版本，重新连接短路分支并执行 R1 |
| 主题库与 P1 命名混淆导致重复建库 | 使用 registry；以现有 dataset 为默认对象 | 删除/停用未使用的重复 dataset 前先确认无真实资料；将其从 Workflow 移除，保留台账记录 |
| P3 资料未经审核被当作正式依据 | 回答标明 P3；P3 不得提升到 P1/P2 无审批 | 移除错误文档或降回 P3，重新索引并复测 |
| 召回阈值导致漏召回或误召回 | 用 R1-R3 和反例连续复测，记录质量样本 | 恢复前一套检索参数；只调整 Dify UI 中的 Top K/分段设置并记录版本 |
| 资料重复导入或临时文件泄露 | 批次台账、文件标识、导入后删除临时目录 | 删除 Dify 重复文档并重新验证；本地临时目录完成清理 |
| Tavily 额度/网络不可用 | 保留知识库路径和清晰失败提示 | 暂停发布联网版本或关闭联网分支，恢复可用的知识库-only 版本 |

Dify 回滚顺序：停止发布当前 draft -> 在 Studio 选择上一已验证版本/草稿 -> Debug 执行 R1、R4、R5 -> 确认可用后再决定是否重新发布。知识库文档删除、移动或重建前必须导出非敏感的文档计数和台账记录；不在 Git 保存导出内容。

## 8. 运营机制与收录规则初稿

### 8.1 日常运营字段

运营台账至少包含：`batch_id`、收集日期、来源系统（如 IMA 或文件交付）、整理人、审核人、目标主题、目标 dataset、文档数量、重复检查结果、索引状态、召回验证问题编号、迁移结果、来源同步标记（如适用）、失败原因、复核日期。台账不包含资料正文、URL 中的敏感参数、凭据或真实地址。

### 8.2 收录规则初稿

1. **可收录内容：**与市场、行业、产品、解决方案直接相关，文本可解析，来源和日期可追溯，经主题负责人确认的资料。
2. **正式主题库：**主题明确、完成去重和基本事实检查后进入对应现有主题 dataset；文件名和文档元数据包含主题、来源类别、日期、版本号等非敏感标识。
3. **P1：**只有业务负责人确认的当前有效、优先参考资料才登记为 P1；P1 是路由优先级，不是新建库的强制理由。
4. **待分类库：**主题无法确认、需要补充审核或来源信息不足的资料进入 `待分类`，回答时必须提示其未审核状态；不能因为召回效果好而自动升级。
5. **实时资料：**需要最新状态的问题走 Tavily；联网结果经过回答节点引用来源，不直接写入知识库。是否收录需按主题规则和人工审核另行处理。
6. **不可直接收录：**空文件、图片-only 且无 OCR 文本、重复文件、明显过期资料、无法确认来源的转载、包含不应进入 workspace 的敏感信息。处理方式分别为补充 OCR/原文、去重、归档/隔离、补充来源或按权限隔离。
7. **更新和删除：**新版本先完成索引和召回，再替换旧版本；删除前记录文档标识和原因，发现误删立即按 Dify 备份/导入记录恢复。
8. **质量门槛：**每批导入 100% `Completed`；抽样至少 2 个问题验证主题正确和片段可读；P1 资料必须有业务负责人确认；失败批次不得打同步标记。
